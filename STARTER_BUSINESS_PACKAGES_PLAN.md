# Generic foundation for tenant-installable business packages

**Approved for implementation · 21 November 2026 · Lastapp baseline `49866ef`**

Build a catalog from which an authorized Tenant user can clone a versioned package into a Space. The user chooses **Business objects** or **Business objects and App**. Both produce tenant-owned entities, rules and business roles. The second also delivers a working App, its micro-apps, and their editable source. A Tenant can add the supplied App later to the objects it already uses.

**Approval covers the generic foundation and its verification with synthetic fixtures. Anton selects the first business application separately.** A package that uses supported capabilities must be publishable and installable through data, source, and compiled assets alone. That is the test of whether the foundation is generic.

## Product contract

| User action | Required outcome |
| --- | --- |
| Install business objects | Publish scoped entities, relationships, rules, and starter role definitions. Allocate no production App, build, or release. Authorized agents can discover and extend the installed model through existing management MCP tools. |
| Install objects and App | Perform the same object installation and activate one App with its declared micro-apps. Its prebuilt client works on the destination App host. The Tenant assigns local users or teams to the appropriate roles. |
| Add the supplied App later | Bind to the original installation’s current local objects. Check the client contract and report incompatibilities. Preserve records, custom fields, assignments, and tenant policy. |
| Customize or use as shipped | Use the prebuilt App immediately after activation and access setup. An authorized author can open a workspace, retrieve the source corresponding to the selected release, edit locally, preview, and deploy. A later author can resume from the tenant-customized release. |
| Install another package or version | Independent packages can coexist in a Space. Explicit dependencies may reuse installed objects. A new catalog version is available for a new clone. Existing installations keep their pinned base and local edits. |

Start with first-party publication, one installation per package key per Space, and one optional App per package. Each App can contain multiple micro-apps. The installer can select an existing Space or use the ordinary authorized Space-creation flow. Initial installation authority belongs to Tenant administrators and authorized Space managers. Tenant members consume Apps with ordinary business roles. Automatic upgrades, three-way merging, third-party publication, and package-supplied server execution are separate product decisions.

## Package and installation contracts

**Package version.** The manifest identifies the publisher, package key, immutable version and digest, format version, required platform/SDK capabilities, inventory of logical items, and any exact dependencies. The objects layer contains canonical Go-backed entity definitions, Space roles, and permission paths. The optional App layer adds App roles and ceilings, ordered micro-app registrations, exact module pins, minimum client requirements, and digests for the static build and editable source. Source includes the entry points, micro-app modules, shared UI, SDK dependency, lockfile, and build command. Package CI produces the static artifact from that source and records the association. The existing hosted configuration supplies the destination App ID and API origin at runtime. [Entity contract](internal/entity/model.go) · [Release manifest](internal/delivery/releases.go) · [Hosted configuration](internal/control/artifacts.go)

**Portable identity.** Give each declared item a stable kind and key inside the package. Bind entity references, role references, App gates, and micro-app parents only at their typed positions. Allocate destination IDs once, before resolving references, so cycles work. Derive permission IDs from the destination entity ID and its permission key. Reject unresolved references and concrete publisher principals, records, assignments, credentials and origins. Leave ordinary labels and literal data intact. Extract the traversal of identity-bearing fields in definitions and App access into the existing entity package. The workspace copier and package binder supply their respective lookup policies. Keep aggregate workspace copying in delivery. Workspace copies can retain eligible same-Tenant references. Package imports require a complete, portable set. Run the authoritative validators after binding. [Existing remapping](internal/delivery/snapshot.go) · [Destination reference checks](internal/entities/entities.go) · [Permission IDs](internal/entity/policy.go)

**Ownership and reuse.** An installation records its Tenant, Space, pinned version/digest, mapped item IDs, accepted operation IDs, and baseline hashes. Distinguish items created by an installation from dependencies owned elsewhere. Check each key, role code, and slug in its actual uniqueness scope. Reuse requires declared identity, compatible version and a matching target contract in the same Space. An unrelated item with the same name is a planning conflict. The first version supports dependencies already installed at an exact version and reports missing prerequisites. It needs neither recursive installation nor version-range solving. [Registry uniqueness](internal/control/migrations/00001_control.sql) · [Entity keys](internal/control/migrations/00003_entities.sql)

**Tenant changes.** The Tenant owns the published objects and its selected release. Installing the optional client later checks required field keys, types, write constraints, and required operations against the current model and approved App contract. Exercise representative role scenarios through the shared evaluator and workspace SDK. Report what can be checked structurally and which scenarios passed. Complex business predicates can depend on individual records. An incompatible contract leads to a workspace customization or an explicit tenant-authored change. Installation cannot grant broader record access to make a client pass. Keep source and base digests available after catalog retirement. Agency over upgrades and destructive changes stays with the Tenant.

## Module boundaries and reuse

Introduce **one new domain package, `internal/apppackages`**, for catalog admission, portability, dependency binding, planning, and installation provenance. Place it above delivery and below the HTTP/MCP adapters. Keep the running system in the current Go service. Both adapters call the same typed methods with the real actor. Delivery accepts a typed plan of changes to a Space and an optional client release. It has no dependency on the catalog or on any business application. Register the new package in the existing dependency test. [Package rules](DEVELOPMENT.md#go-package-boundaries) · [Layer enforcement](internal/layering_test.go)

## Planning, activation, and recovery

1. **Publish and inspect.** Admit the bundle through a trusted first-party publishing identity. Verify format, declared capabilities, dependency closure, item counts, path and byte limits, and artifact digests. Store immutable content before publishing its catalog entry. Republishing identical content is idempotent. Reusing a version with different content is a conflict. Runtime reads come from the approved catalog.
2. **Plan.** An authorized caller selects the version, mode, destination, and bindings. Return the proposed writes, dependencies, key conflicts, quota costs including workspace storage, and changes in effective access. Identify existing Apps with inherited Space permissions that could expose the new objects. Planning is read-only. Bind the review digest to versioned inputs, mode, target, bindings, and current Space base. Apply reauthorizes the caller and recomputes the plan. A digest identifies the reviewed content and carries no authority.
3. **Stage and preview.** Use an owned workspace and persist stable item mappings across retries. Validate the resolved definitions as a set. For the full mode, materialize the verified bytes as a destination-owned build, capture a release, and offer preview. Freeze the staged revisions and the exact write set. Recheck prerequisites, including prerequisites shared with another package. Unrelated workspace edits must be reconciled or excluded from the frozen operation. The objects-only path can proceed without hosting configuration.
4. **Activate.** Under the existing Tenant-first lock order and Space mutation guard, check the reviewed base, quotas, and live human/delegated production authority. Queue a durable operation and return its ID. The worker rechecks live authority before privileged work. Prepare affected physical tables and versions, then activate entity ACLs, role states, App policy, and the optional release selection in the final registry transaction. Derive the installed mode from successful activation. A failed attempt to add an App leaves the prior objects-only installation usable. Avoid writes or revision bumps to sibling resources outside the plan. [Existing activation guarantees](WORKSPACES.md#releases-and-production-changes)
5. **Recover.** Identical request keys and payloads return the original operation. A reused key with a different payload fails. A unique installation per Space/package also handles competing requests with different keys. Workers resume from persistent operation state and stable IDs. After a lost commit acknowledgment, read the durable outcome before retrying. For an already accepted request, authorize access to its receipt and return its recorded outcome before evaluating a new plan against a now-changed base. A new activation against a changed base requires replanning. Reuse existing physical version fences and compatible-layout recovery across the registry/business-database boundary. Publish the failed step, retry eligibility, and audit attribution to both transports.

**Registry migration.** Today both the release ID and target App ID are required on each deployment, and prepared entity versions point at its ID. Extend that operation in place with a versioned plan and a checked kind for ordinary release, objects-only install, full install, and later App attachment. Constrain the optional references by kind. Preserve existing IDs, queued jobs, receipts, retries, and status APIs. Add catalog-version, installation, item-mapping, and release-source records with scoped foreign keys and uniqueness constraints. Link installation attempts to the common operation and derive status from it to avoid two competing job states. Land forward-compatible readers and migrate existing rows before enabling new producers. In a mixed deployment, gate new jobs until all workers can read them. [Deployment schema](internal/control/migrations/00010_releases.sql) · [Deployment recovery](internal/delivery/deployments.go)

## Author and end-user access

Expose browse, inspect, plan, stage, activate, status, attach-App, and retrieve-source operations through the shared service. Return paginated metadata and short-lived scoped downloads for large files. Agent actions remain bounded by the delegating user's live permission and the grant. A workspace author can prepare and preview within their grant. Production activation requires separate production authority. Binding a Space, allocating storage, assigning a manager, and assigning business roles each use their existing authorization checks.

Keep discovery and permission catalogs generated from the same Go contracts used at execution. The console renders server-owned plan diagnostics and capabilities. Starter business roles begin unassigned. The review also exposes permission paths granted by membership or record relationships. **Set up access** uses the existing assignment APIs and shows the results independently of installation success. **My Apps** lists active deployed Apps intended for the member through the configured discovery roles and effective team membership. Direct-link launch retains the existing membership and approved-origin checks. The data API enforces App, record and field permissions on every request. Management MCP discovers the installed definitions and contracts for building a custom client. [Role model](FOUNDATION.md) · [App sessions](internal/dataapi/sessions.go)

**Customize** resolves the active release to its private source. Generate workspace configuration at download, test through the App SDK, then upload the edited source and build as a new immutable release pair. Keep workspace source private to its authorized author/grant until deployment. An authorized subsequent author can retrieve deployed source in their own workspace. Resolve all downloads by authorized installation, workspace or release before serving bytes by digest.

## Capacity and operations

- **Bound work at admission.** Reuse current entity, metadata, workspace, release, and artifact limits. Define package-specific limits once in the Go capability catalog for manifest bytes, items and dependencies, source size, and pending operations. Check them before expensive work and recheck mutable quotas under lock. Bound stored and expanded source bytes. [Delivery limits](internal/delivery/policy.go) · [Artifact limits](internal/artifact/store.go)
- **Keep cost local.** Index catalog versions, installation and operation lookup, item ownership, and active jobs. Scope package queries by Tenant and Space. A package install has a bounded destination-Space baseline read for compatibility with current workspace capture. Batch reads by resource kind. Preparation and writes operate on declared items. Catalog growth and unrelated Tenant inventories must not increase rows scanned by an install lookup.
- **Keep large transfers out of transactions.** Validate and stage immutable bytes before committing metadata links. Deduplicate physical content by digest while enforcing logical ownership on every read. Retain bytes reachable from installations or releases, including archived catalog versions. Remove abandoned staging artifacts after a grace period using a recheck of live references.
- **Use the existing worker model.** Preserve Tenant fairness, deployment ordering and bounded connections. Surface queue age, phase duration, item/byte counts, stale plans, failures and retries with an operation ID. Measure at configured bounds before proposing higher concurrency. [Worker scheduling](DEVELOPMENT.md#background-worker)

## Implementation sequence and acceptance gates

| Phase | Deliverable | Evidence required to advance |
| --- | --- | --- |
| 1. Package contract and catalog | Immutable publishing, validation, inspection, and two unrelated synthetic package fixtures. One includes a cycle of entity references and an optional App with two minimal micro-apps. | Publish both via the same entry point. Verify idempotent publication, digest mismatch rejection, typed remapping, and compatibility diagnostics. Changing fixture content requires no framework change. |
| 2. Destination planning and provenance | Read-only plans for both modes, installation identity and mappings, exact dependency binding, and authorization-aware review. | Repeated plans on the same base match. Test two Tenants, same-name conflicts, explicit shared dependencies, stale bases, quota boundaries, and inherited access in a sibling App. |
| 3. Shared activation and objects-only installation | Migrate the existing worker and enable scoped, App-optional activation. | Run old and new jobs on a disposable registry. Verify no production App for objects-only, no sibling writes, and one operation under concurrent requests. Interrupt before and after DDL and final commit, revoke delegation mid-job, retry, and reconcile the recorded outcome with actual data access. |
| 4. Optional App and tenant-owned source | Full install, later attachment, private release source, workspace preview and customization. | Launch the same compiled build under two distinct App IDs. Attach to an edited objects-only install with real fixture records. Accept compatible edits and report incompatibilities without overwriting data or widening ACLs. Reopen one Tenant’s customized release as another authorized author and verify isolation from the second Tenant. |
| 5. Interfaces and operational qualification | Deliver the Console and MCP flows, role setup and My Apps. Update the current guides, generated contracts and package-author documentation. | Exercise manager, ordinary user, and delegated agent end to end. Check parity of both management entry points, source download scope, allowed/denied record operations, and revocation. Run the normal lint, race/integration and browser suites on disposable infrastructure. |

**Scale gate.** Exercise a manifest at its supported limits and one just over them. Inspect query plans with unrelated Tenant/catalog rows added. Queue work for multiple Tenants with one waiting on storage and verify another makes progress. Record query counts, rows examined, peak memory, connection use, and queue/activation timings for the tested limits. A new unbounded scan, byte transfer under a registry lock, or operation that multiplies work by unrelated Tenant count blocks release.

**Definition of done.** Two synthetic packages pass the same publish, install, and customization flows. Two Tenants can independently own the same package. Both install modes work, an objects-only installation can acquire its App after compatible local edits, and existing releases still deploy and recover. The resulting foundation can accept whichever business application Anton selects next.
